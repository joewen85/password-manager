# 分类同步契约

本文档定义分类元数据在 Android、HarmonyOS、iOS、macOS 以及 Windows/Linux
共享 native core 之间的同步语义。目标是保证分类删除在任意后续自动或手动同步中都不会
因旧快照、旧 revision 或条目中的旧分类引用而复活。

## 快照字段

`VaultSnapshot.categoryStates` 是加密快照中的新增可选数组。同步 envelope 版本保持为 1，
因为该字段位于已加密的 snapshot 内部，旧快照缺少该字段时仍可读取。

每个状态包含：

| 字段 | 含义 |
| --- | --- |
| `name` | 去除首尾空白后的分类名，比较时忽略大小写。 |
| `isDeleted` | `true` 表示分类删除墓碑。 |
| `updatedAt` | 展示和确定性平局处理使用的时间；不作为新旧状态的主要依据。 |
| `version` | `deviceId -> counter` 版本向量。 |
| `updatedBy` | 最后写入该状态的设备 ID。 |

## 合并规则

1. 先比较版本向量。支配另一方的状态直接胜出。
2. 版本相等或并发且活动/删除冲突时，删除胜出（remove-wins）。
3. 两边同为活动或同为删除时，按冲突策略选择内容；结果合并双方版本向量以保证收敛。
4. 显式重新创建同名分类必须在已有墓碑版本上递增当前设备计数，因此新活动状态支配旧墓碑。
5. 只有客户端已经建立同步基线时，`hasLocalChanges` 才能用于从旧格式的“缺失”推断首次删除；
   全新安装首次同步不得把远端存在、本地缺失的分类解释为本地删除。同步基线由非零
   `lastSyncRevision`、非空 `lastRemoteFingerprint`，或成功状态对应的 `lastSyncAt` 表示；
   失败、跳过等未成功尝试写入的同步时间不构成基线。
6. 合并结果与远端是否相同只比较业务字段：`entries`、`categories`、`categoryTemplates`、
   `categoryStates`、`tags` 和 `security`。`syncStatus`、备份状态和快照级 `updatedAt` 是本机运行时
   元数据；仅这些字段不同不得上传新 revision，否则每次同步状态落盘都会造成 9 -> 10 -> 11
   的无意义写回，并持续重新处理同一个删除墓碑。
7. 分类的字段模板与该分类共用 `CategorySyncState.version`。新增、删除、重命名或改型字段、应用
   分类预设，以及导入合并改变模板时，都必须递增当前设备的分类版本。模板合并先比较对应分类
   的版本向量：一方支配另一方时直接选择支配方模板；只有版本相等或并发时才应用冲突策略和
   `updatedAt` 平局规则。同步 envelope 的 revision 只表示整个远端文件的写入顺序，不表示某个
   分类模板的因果新旧。

旧格式缺失状态的推断规则：

- 没有同步基线时，不从任何单边缺失推断删除；即使双方 revision 都为 0，也不得用本地空快照
  直接覆盖已有远端快照。
- 本地有未同步修改，远端存在本地缺失的活动分类：本地生成删除墓碑。
- 本地已干净且策略为 `remoteWins`，远端缺少仅本地存在的活动分类：生成远端删除墓碑。
- `keepBoth` 不从干净快照的单边缺失推断删除。

## 派生数据

`categories` 和 `categoryTemplates` 只包含最终活动状态允许的分类。合并后的活动条目如果仍引用
已删除分类，客户端必须清空该引用，并递增条目自己的版本向量。这样即使旧远端条目仍带有
`category = "test"`，重建分类集合时也不能绕过墓碑把 `test` 再次加入。

标签不使用本契约。标签仍按现有集合合并规则处理。

## 旧数据迁移

缺少 `categoryStates` 的快照会从 `categories`、`categoryTemplates` 和活动条目的分类引用合成
`version = {"legacy": 1}` 的活动状态。下一次需要写回远端时会上传包含状态的快照。

迁移期间必须更新所有仍会写入同一远端保险库的维护中客户端。旧客户端无法表达分类墓碑；
它可以读取新增字段所在的快照，但重新写入时可能丢弃该字段。新客户端不得仅依赖 revision 或
设备时间恢复删除状态。

## 必需回归场景

- 全新安装没有同步基线但被标记为本地有修改时，首次同步保留远端分类、分类模板和活动状态；
  覆盖远端 revision 为 0 和大于 0，以及 `remoteWins`、`keepBoth` 两种策略。
- 删除分类，首次同步成功并清除 dirty 标记，再接收更高 revision 的同一旧远端快照。
- 上述场景分别使用 `remoteWins` 和 `keepBoth`。
- 本地和远端只存在同步状态、备份状态或快照时间差异时，接受远端 revision 且不上传下一 revision，
  同时保留分类墓碑。
- 旧远端活动条目仍引用已删除分类。
- 删除墓碑与并发活动状态合并，验证 remove-wins 和版本向量 join。
- 显式重建同名分类，验证新状态支配旧墓碑。
- 本地新增分类字段并完成同步后，接收 envelope revision 更高但分类版本更旧的模板；字段不得丢失，
  且 `remoteWins`、`keepBoth` 都必须遵守分类版本向量。
- 模板字段删除来自分类版本更高的一侧时，旧字段不得因另一侧仍保留模板而复活。
- 缺少 `categoryStates` 的旧快照可读取，并在 JSON 往返后保留合成状态。
